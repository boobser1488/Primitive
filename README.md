Воксельная игра на Rust: клиент на wgpu + авторитативный сервер на tokio. Одиночная игра и сетевая — на одном и том же сервере.

## Быстрый старт

```bash
cargo run --release -p primitive_client
```

Открывается меню: **Singleplayer**, **Multiplayer**, **Settings**, **Quit**. Одиночная игра не требует ничего запускать вручную — клиент поднимает сервер внутри себя.

Ничего из этого не требует лезть в файлы: миры создаются и удаляются на экране, серверы добавляются и правятся на экране, настройки меняются на экране. Файлы рядом с бинарником — это формат хранения, а не интерфейс.

Отдельный сервер для сетевой игры:

```bash
cargo run --release -p primitive_server
```

При первом запуске каждый создаёт рядом с собой файл настроек со всеми значениями по умолчанию — отредактируйте и перезапустите:

- клиент — `client_settings.toml`
- сервер — `settings.toml`
- список серверов — `servers.toml` (правится прямо в игре, руками трогать не обязательно)

Имена клиента и сервера **разные намеренно**. Раньше оба читали `settings.toml` из текущей папки, и при запуске из корня workspace (а именно так работает `cargo run -p ...`) они дрались за один файл: кто стартовал последним, тот перезаписывал его своими значениями по умолчанию. Старый `settings.toml` клиент прочитает один раз и перенесёт настройки в новый файл, ничего не удаляя.

Проверки:

```bash
cargo test --workspace
cargo run -p primitive_server --example verify_broadcast   # сервер должен быть запущен
cargo run -p primitive_server --example verify_broadcast -- 127.0.0.1:7899   # или на другом порту
cargo run -p primitive_client --example gen_placeholder_textures
```

## Управление

| Клавиша | Действие |
|---|---|
| WASD | движение |
| Мышь | обзор (клик — захват курсора) |
| Пробел | прыжок (тратит выносливость); в воде — грести вверх (удерживать) |
| ЛКМ / ПКМ | сломать / поставить блок; ЛКМ по игроку — ударить; ПКМ по ящику — открыть |
| Alt + ПКМ | положить **один слой** сыпучего вместо целого блока |
| 1–9, 0, колесо | выбор блока |
| Esc | пауза (продолжить / настройки / выйти в меню / выход) |
| F | туман вкл/выкл |
| F3 | панель статистики на экране |
| F11 | полный экран (безрамочный, запоминается) |
| /help в чате | список команд |

В меню работают и мышь, и клавиатура: стрелки и Enter, Esc — назад. В списке миров дополнительно **N** — создать, **Del** — удалить; в списке серверов **A** — добавить, **E** — изменить, **Del** — удалить.

## Миры

Кнопка Singleplayer открывает список миров. Мир — это папка в `saves/` с файлом `world.toml`, где лежат его имя и сид, рядом с тем, что пишет туда сервер.

**Сид хранится с миром, а не в настройках клиента.** Сид *и есть* мир: изменив его, вы уроните сохранённые правки на совершенно другой рельеф. Пока мир был один, сид в конфиге ещё имел смысл; с несколькими это гарантированный способ испортить чужой ландшафт, открыв соседний мир.

Имя мира и имя папки — разные вещи. Папка обязана быть безопасной для файловой системы, имя — нет: мир называется `My World #2` и живёт в `my-world-2`. Два мира с одинаковым именем получают разные папки, иначе второй молча открывал бы сохранение первого.

Удаление стирает дерево каталогов, поэтому вокруг него два барьера. Экран подтверждения, на котором **Enter намеренно ничего не подтверждает** — Enter нажимают не читая, и это не должно удалять мир. И проверка в самом коде: удаляется только прямой подкаталог папки сохранений, и только если в нём есть `world.toml`.

Папка из прежней версии (когда мир был один и задавался путём в настройках) подхватывается как мир — и если она лежит внутри `saves/`, и если настройки всё ещё указывают прямо на неё.

## Настройки в игре

Экран Settings меняет то, ради чего стоит нажимать кнопку: имя, дальность прорисовки, поле зрения, чувствительность мыши, вертикальную синхронизацию, туман, ambient occlusion и дальность локального мира. Изменения применяются сразу и записываются в `client_settings.toml`, когда вы уходите с экрана — отдельной кнопки «сохранить», о которой можно забыть, нет.

Сразу — это важная часть: переключатель vsync, ради оценки которого надо перезапускать игру, не переключатель, а число. Поэтому смена vsync переконфигурирует поверхность на месте, а поле зрения обновляет камеру в том же кадре.

Пара десятков остальных параметров (пропорции тумана, бюджеты мешинга, рабочие потоки) остались в файле — там уже живут те, кто их трогает.

## Одиночная игра

Кнопка Play поднимает **настоящий сервер внутри процесса клиента**, на `127.0.0.1` и на порту, который выдаёт система, и подключается к нему.

Причина такая: альтернатива — отдельный офлайн-путь в клиенте — это второй генератор мира, вторая физика и вторая симуляция песка, и они расходятся. Здесь реализация мира ровно одна, а одиночная игра отличается от сетевой только тем, чей это процесс. Цена — сокет на loopback, и она несопоставимо меньше.

Локальный мир отличается тремя вещами:

- **порт 0 на loopback** — мир недоступен из сети, и две копии игры спокойно работают рядом;
- **без плагинов** — не «отключены», а не собраны: клиент подключает `primitive_server` с `default-features = false`, и движка скриптов в бинарнике игры нет вовсе;
- **без античита** — он существует, чтобы клиент не врал серверу, которым не владеет; здесь это один процесс, и включённый античит мог бы только оттащить игрока назад из-за разногласия с самим собой.

Миры лежат в `saves/` — отдельно от `world/` обычного сервера, иначе запуск сервера из той же папки затёр бы вашу игру. Выход из мира через паузу ждёт сохранения, а не бросает его на полпути.

Фоновые циклы сервера (тик, автосохранение, статистика) завершаются по сигналу остановки, а не живут до конца процесса. Для отдельного бинарника это незаметно — его остановка и есть конец процесса, — но клиент поднимает и гасит сервер на каждую сессию, и оставленный тик-луп продолжал бы тикать, сохранять и симулировать весь остаток игры.

## Интерфейс

Меню, пауза и панель F3 рисуются одним пайплайном — тем же, что и хотбар. Ни второго шейдера, ни второго буфера, ни второго набора состояний смешивания, которые пришлось бы держать в согласии.

Текст — растровый шрифт 6×9 **данными**: 95 глифов по 9 байт, без файла шрифта и без зависимости. Из этих данных при старте собирается атлас: по слою на символ в уже существующем массиве текстур блоков, и символ рисуется одним текстурированным квадратом.

Сначала было проще — квадрат на каждый зажжённый пиксель. Это оказалось дорого ровно там, где заметно: около двенадцати квадратов на символ, панель F3 — 46 500 вершин и 1.4 МБ, пересобираемых и заливаемых каждый кадр. При нескольких сотнях кадров в секунду интерфейс стоил больше, чем мир за ним. В абстракции расточительно и совершенно неважно здесь: полный экран текста — несколько тысяч треугольников, один раз за кадр, на экране, который в основном не рисует мир.

Две вещи в нём стоит назвать, потому что обе заменили худшее. **Выносные элементы настоящие**: прошлый шрифт был 5×7 без места под базовой линией, и `g j p q y` вжимались в неё — любое слово с ними (`player`, `singleplayer`, имя игрока) читалось как набранное капителью с несколькими сломанными буквами. **Просвет живёт внутри ячейки**: шестая колонка пуста у каждого глифа, а не добавляется между ними, поэтому текст стоит на фиксированной сетке в 6 пикселей. `_` — намеренное исключение: он занимает все шесть, чтобы подчёркивания сливались в сплошную линию.

Вертикальная выключка считается по высоте прописных, а не по высоте ячейки: две строки выносных пусты почти у всех символов, и центрирование по всей ячейке заметно опускало бы каждую надпись.

### Фон меню

Настройка **MENU BACKGROUND** выкладывает за меню плитку из блоков — на выбор камень, земля или булыжник. **По умолчанию выключена**: стена текстуры за мелким текстом стоит читаемости, и это размен, на который игрок должен пойти сам, а не получить его при первом запуске. Пока фон выключен, строка выбора блока показана серой — знать, что опция есть, важнее, чем прятать её.

За экраном паузы фон не рисуется никогда: там уже есть мир, и он лучше любых обоев.

Геометрия задаётся так, будто окно квадратное (вершинный шейдер делит x на соотношение сторон), поэтому ширины считаются в долях **высоты** экрана: меню не растягивается на весь ультраширокий монитор. Позиция курсора переводится в те же координаты ровно обратным преобразованием — и это покрыто тестом, потому что рассинхрон здесь даёт кнопки, которые нажимаются не там, где нарисованы, и только при некоторых размерах окна.

Раскладка и таблица попаданий строятся одним проходом: два прохода расходятся, а меню, чьи кнопки нажимаются в паре пикселей от того места, где нарисованы, хуже, чем меню вообще без мыши.

## Когда что-то ломается

Игру не запускают из терминала. Напечатать в stderr и выйти — то же самое, что исчезнуть без объяснений: окно пропало, консоли, куда всё написалось, никто не открывал, и игроку нечего сообщить, кроме «оно закрылось».

Поэтому всё, что доходит до `crash.rs`, делает две вещи: пишет `crash.log` рядом с исполняемым файлом и говорит об этом при выходе. Рядом с бинарником — потому что это папка, которую игрок распаковал и сможет найти снова; рабочий каталог у игры, запущенной двойным щелчком, там, где его оставила оболочка. Файл дописывается, а не перезаписывается, и ограничен по размеру, чтобы цикл падений не забил диск.

Обработчик паник **дополняет** стандартный, а не заменяет: тот печатает backtrace при `RUST_BACKTRACE`, и это ровно то, чего файл заменить не может.

Что до `crash.rs` **не** доходит — то, что обработано в игре. Отказ сервера, кик и потеря соединения возвращают в меню с причиной на экране. Раньше кик закрывал клиент, а оборванное соединение оставляло замерший мир без единого объяснения.

## Список серверов

Список правится в игре и пишется в `servers.toml` при каждом изменении. Раньше он жил только в файле: добавить сервер значило выйти, найти файл, поправить TOML руками и запустить заново, а опечатка в нём молча откатывала весь список к значению по умолчанию.

Форма проверяет ввод: адрес обязателен, а голый хост без порта дополняется до `:7878`, потому что это самая частая ошибка и исправление очевидно. Пустое имя заменяется адресом. Отклонённая форма ставит курсор в то поле, которое надо исправить, а не просто отказывает.

Подключение идёт **в фоне**: недоступный сервер отваливается по таймауту через десять секунд, и всё это время окно продолжает рисоваться и отвечать. Ошибка показывается на экране с переносом длинных строк и кнопкой повтора, а не улетает в консоль, которую никто не видит.

## Прозрачность: вырезание и смешивание

Это две разные вещи, и путать их нельзя.

**Вырезание (cutout)** — листва. У её текстуры каждый тексель либо полностью непрозрачен, либо полностью отсутствует, поэтому пустые просто отбрасываются (`discard`). Это идёт в обычном непрозрачном проходе и продолжает писать глубину — потому дерево рисуется в любом порядке. Раньше `discard` не было вовсе, и прозрачные тексели рисовались сплошным цветом: дерево выглядело кубом.

Отдельно: листва **не** отсекает грани против соседней листвы. Грань между двумя блоками листвы — это как раз то место, где виден вырез, и её отсечение делало крону толщиной ровно в один блок, сквозь которую видно насквозь.

**Смешивание** — вода. Помечается в вершинах при построении меша и рисуется вторым проходом: альфа-смешивание, запись глубины выключена, отсечение задних граней выключено (иначе из-под воды не видно её поверхности сверху). Проходы сортируются от дальнего к ближнему, потому что при смешивании порядок отрисовки — это и есть порядок наложения.

Меш чанка хранит и то и другое в **одном** буфере вершин и одном буфере индексов, а граница между проходами — просто число. Два буфера удвоили бы количество аллокаций на чанк ради нескольких граней воды.

```
primitive/

│   ├── fluid.rs                # вода как уровень: сколько в ячейке и куда оно пойдёт

│   └── net.rs                  # bincode с префиксом длины

│   ├── lib.rs                  # процесс: приём соединений, тик-луп, метрики, автосохранение

│   ├── settings.rs             # ~30 параметров + секция [anticheat]
│   ├── net/                    # СЕТЬ
│   │   ├── connection.rs       # рукопожатие, чтение, запись, подкачка чанков
│   │   └── players.rs          # реестр, очереди, индекс подписок на чанки
│   └── logic/                  # ЛОГИКА: всё, о чём сервер решает сам

│       ├── anticheat.rs        # скорость, полёт, телепорт, дальность, рейт-лимиты
│       ├── commands.rs         # команды консоли и чата с уровнями прав

└── primitive_client/src/
    ├── main.rs                 # цикл: ввод -> физика -> сеть -> меш -> рендер
    ├── settings.rs, crash.rs, embedded.rs
    ├── engine/                 # ДВИЖОК: всё, что говорит с GPU
    │   ├── renderer.rs         # проходы: сплошной, вырез, смешивание, актёры, UI

    │   ├── texture.rs          # массив текстур блоков и глифов
    │   ├── camera.rs, frustum.rs, sky.rs, font.rs
    │   └── shader.wgsl, actor.wgsl, overlay.wgsl, hotbar.wgsl
    ├── net/                    # СЕТЬ
    │   ├── network.rs          # сокет, фоновые чтение и запись, очереди
    │   └── remote_players.rs   # другие игроки и интерполяция между снапшотами
    ├── ui/                     # ИНТЕРФЕЙС
    │   ├── widgets.rs          # панели, кнопки, поля ввода, текст
    │   ├── menu.rs             # меню, миры, серверы, настройки, пауза
    │   ├── hud.rs, hotbar.rs, chat.rs, inventory_screen.rs, debug.rs
    │   └── input.rs, keybinds.rs
    └── logic/                  # ЛОГИКА клиента (рабочая копия, не истина)
        ├── chunk_manager.rs    # запросы с повторами, выгрузка, доступ к блокам
        ├── physics.rs, mining.rs, stamina.rs, shake.rs
        ├── entities.rs         # приём, интерполяция, отрисовка сущностей
        ├── inventory.rs        # снимок инвентаря, присланный сервером
        └── worlds.rs           # список миров на диске
```

Границы слоёв описаны в `mod.rs` каждого каталога: что в него входит, чего
в нём быть не должно, и почему. Правило, которое их связывает: **движок не
знает про игрока, интерфейс ничего не решает, а логика клиента ни на что не
влияет — истина у сервера, а общие правила лежат в `primitive_shared`.**

## Освещение

Свет живёт в **мировых координатах** и сохраняется между построениями мешей: считается один раз при загрузке чанка, дальше обновляется инкрементально. Один байт на ячейку — небесный свет в младшем полубайте, блочный в старшем.

### Почему прошлую версию пришлось переписать

Старый вариант освещал по одному чанку в объём «чанк + рамка в 1 блок», пересобирая его при каждом ремеше. Это было одновременно **неверно и медленно**:

- **Неверно.** Свет распространяется на 15 блоков, рамка в 1 блок его не переносит. Светокамень в двух блоках внутри соседнего чанка для этого чанка просто не существовал — на шве получался жёсткий разрыв освещения. То же с небесным светом под навесом, начинающимся в соседнем чанке.
- **Медленно.** Каждая пересборка — 18×64×18 = 20 736 ячеек с двойной заливкой. Ремеш чанка каскадом задевает 8 соседей (у них меняются грани на стыке), так что **один клик стоил девяти полных пересчётов света** — около 190 тыс. ячеек BFS на одно нажатие.

Теперь правка блока трогает ровно тот объём, до которого свет реально дотягивается, а построение меша — чистое чтение.

### Две ошибки, найденные property-тестом (четвёртый заход)

Гадать надоело, поэтому я написал свойство: **свет, обновлённый инкрементально, должен совпадать со светом, посчитанным с нуля**. Иначе мир выглядит по-разному в зависимости от того, что игрок успел сделать, — ровно симптом «иногда неправильно». Тест сразу упал и выдал две настоящие ошибки:

1. **Незагруженный чанк читался как полный дневной свет.** Это было решение для отрисовки, оказавшееся не в том месте: код распространения света читает через ту же функцию, поэтому незагруженный сосед вёл себя как вечный источник силы 15. Свет затекал вбок из ниоткуда в замурованный камень — выдолбите карман внутри холма рядом с границей прогрузки, и он оказывался освещённым. Видно это было только у края загруженной области, потому и выглядело случайным. Теперь незагруженный чанк — темнота, а светлую границу рисует мешер, где этому и место.

2. **Разбитый блок не подхватывал свет от соседей.** При правке блока небесный канал заново засеивался от соседних ячеек, а блочный — нет. Сломанный блок открывает ячейку, у которой своего света не было: `remove` возвращал пустой список, излучения тоже нет, и ячейка оставалась чёрной даже с светокамнем вплотную. Чем больше копаешь, тем шире расползалась темнота.

Оба случая закреплены отдельными регрессионными тестами, плюс само свойство прогоняется на 400 случайных правках в четырёх чанках.

### Третья ошибка: колонка и заливка считали по-разному (пятый заход)

Property-тест был расширен блоками с **частичной непрозрачностью** — водой и листвой. Он снова упал, и снова по делу: проход по колонке нёс солнечный свет вниз, вычитая только непрозрачность блока, а заливка вдобавок брала стандартную единицу за шаг. Под водой и под листвой два пути давали разные значения; там, где свет идёт в полную силу, они совпадали — поэтому все прежние тесты и проходили. Теперь оба пути идут через один helper `sky_below`.

Итого property-тест нашёл три ошибки, которых не находили обычные тесты. Он же теперь и стережёт: 400 случайных правок сверяются с полным пересчётом.

### Плавное освещение (третий заход)

Свет брался один раз на грань и применялся ко всем четырём её вершинам — то есть освещение было плоским на каждый квад. Светокамень давал жёсткий квадрат света со ступеньками, а стена, освещённая сбоку, меняла яркость целыми блоками.

Теперь свет усредняется **по вершине**: для каждого угла берутся четыре ячейки, которые его касаются, непрозрачные пропускаются. Пропускаются, а не считаются тёмными: блок за стеной не должен затемнять освещённую грань перед ней. Затемнением углов занимается ambient occlusion, и он считается по тем же трём соседям, так что они согласованы по построению. Значение меняется вдоль квада, и видеокарта интерполирует его в градиент бесплатно.

### Детали

- Два канала раздельно, потому что ведут себя по-разному: небесный модулируется временем суток, блочный нет. Шейдер делает `max(небо × яркость_дня, блок)` — цикл суток не требует перестройки мешей вообще.
- Солнечный свет **вниз идёт без затухания**: луч достигает дна шахты неослабленным, вбок затухает обычным образом. Без этого дно двадцатиблочного колодца получалось почти чёрным.
- Удаление света — отдельный проход с последующим дозаполнением от уцелевших источников. Иначе сломанный факел оставляет за собой «призрачное» свечение, а закупоренная шахта — висящий освещённый столб.
- Ambient occlusion по трём ячейкам, касающимся угла вершины, с переворотом диагонали квада при анизотропном AO — иначе на затенённых углах вылезает классический диагональный шов.

## Туман

Экспоненциально-квадратичный по расстоянию, цвет привязан к цвету неба и меняется вместе с ним. **Цвет очистки кадра равен цвету тумана** — именно это растворяет границу прогрузки в горизонте вместо видимой стены. Под водой туман отдельный: ближе и зеленовато-синий.

Дистанции тумана считаются от радиуса прорисовки, а не задаются в блоках: иначе игрок, увеличив дальность, упирался бы в стену тумана с чистой геометрией за ней.

## Текстуры граней: ориентация

Была реальная ошибка. UV-координаты брались из одного общего массива `FACE_UVS` и применялись ко всем шести граням, а каждая грань перечисляет свои углы в собственном порядке обхода. В результате одни и те же четыре UV попадали на разные углы у разных граней: боковые текстуры оказывались **повёрнуты на 90°**, часть — зеркально. На однотонном камне это незаметно, а на боковой текстуре травы зелёная полоса шла вертикально.

Правило теперь явное: `v = 0` — верх изображения, поэтому на любой вертикальной грани `v` следует за `1 - y`, а `u` растёт вправо **с точки зрения наблюдателя снаружи блока** — а это разная мировая ось для каждой грани:

| грань | наблюдатель смотрит вдоль | его «вправо» | u | v |
|-------|---------------------------|--------------|---|---|
| +Y | вниз | +X | x | z |
| -Y | вверх | +X | x | 1 - z |
| +X | -X | -Z | 1 - z | 1 - y |
| -X | +X | +Z | z | 1 - y |
| +Z | -Z | +X | x | 1 - y |
| -Z | +Z | -X | 1 - x | 1 - y |

Четыре теста фиксируют это: верх текстуры на верху блока, боковые грани не повёрнуты, каждая грань покрывает текстуру ровно один раз, противоположные грани не зеркальны друг другу.

## Хотбар

Девять слотов внизу экрана, каждый показывает **настоящую текстуру** блока, который поставит правая кнопка. Тот же массив текстур, что и у мира — отдельный атлас иконок разъехался бы с текстурами блоков при первой же их замене.

Выбор: клавиши 1–9 или колесо мыши. Выбранный слот подсвечивается рамкой и рисуется в полную яркость, остальные приглушены. Слоты, рамки и подсветка идут одним draw call: вершина с `tex_layer = 0xFFFFFFFF` рисуется плоским цветом вместо выборки из текстуры.

Иконка берётся с **боковой** грани, а не с верхней: для травы именно бок с зелёной кромкой над землёй узнаётся в размере иконки.

## Инвентарь и хранилище

**Список рецептов — окно в список, а не весь список.** Панель росла
вместе с ним, и четырнадцатый рецепт вытолкнул экран за нижний край
квадратного окна. Теперь колесо мыши листает, сбоку полоса прокрутки,
сверху «5-12 OF 14», а высоту экрана задаёт сетка слотов и только она:
рецепты будут добавляться и дальше, а меню, которое от каждого
добавления становится выше, однажды перестанет рисоваться вовсе.

**У сундука есть STORE ALL и TAKE ALL.** Высыпать полный рюкзак стоило
сорока shift-кликов, и игрок их считал. Это одно сообщение, а не сорок:
пачка из сорока — ровно то, ради чего существует ограничение частоты
сообщений, а перевод, применившийся наполовину из-за потерянного
сообщения, хуже неприменившегося. Кнопки стоят в промежутке между двумя
сетками и стрелкой показывают, куда поедет; стопка, взятая в руку,
кладётся обратно, а не уезжает со всем остальным.

## Ящики: первый блок, у которого есть содержимое

Ячейка мира — один `u16`, и весь оверлей правок построен на этом: правка это `(индекс, id)`, а выселенный чанк восстанавливается генератором плюс оверлеем. Сундук в эту схему не влезает, и это хорошо: его содержимое лежит **рядом**, по позиции блока, в отдельном файле `chests.bin`, а мир продолжает хранить только идентификаторы.

Отдельный файл, а не поле в `edits.bin`, по одной причине: у сохранения мира есть версия, и её повышение заставляет сервер **отказаться** грузить старый мир. Для игрока это все его постройки разом. У мира, сделанного до сундуков, просто нет второго файла — и это ровно «сундуков нет». Мигрировать нечего, потерять нечего.

Пустой сундук не хранится: запись появляется, когда в него кладут, и исчезает, когда забирают последнее. Иначе размер сохранения растёт от того, сколько **построено**, а не от того, сколько лежит — при том что «стоит ли здесь сундук» и так отвечает сам блок.

**Двое у одного ящика.** Клиенту не отвечают «принято» — ему отвечают содержимым, и то же уходит всем, кто в него смотрит. Один код пути, никакой возможности увидеть разное, и никакой предсказательной логики на клиенте, которую пришлось бы откатывать. Взятие в руку это номер слота, поэтому если сосед изменил слот между «взял» и «положил», жест отменяется — иначе он завершился бы против того, что там оказалось, и человек выбросил бы то, чего не трогал.

Сообщения, двигающие вещи, несут **сторону и слот, но не позицию**. Сервер помнит, какой сундук этот игрок открыл, и проверяет на каждом жесте: жив ли, там ли ещё сундук, дотягивается ли (по своим копиям позиций). Клиент не может залезть в сундук, который не открывал, потому что ему нечем его назвать.

## Вода: поверхность ниже блока

Хождение по воде, о котором вы писали, — это **не** физика. Тесты против настоящего генератора мира (не искусственного бассейна, а сгенерированного океана на четырёх сидах) показывают, что игрок тонет и ложится на дно.

Проблема была в отрисовке: вода рисовалась полным непрозрачным кубом. У берега глубина почти везде один блок, и такой куб выглядит как сплошная поверхность ровно на уровне ступней — стоя *в* воде, выглядишь стоящим *на* ней. Теперь верхний слой жидкости рисуется чуть ниже полного блока, боковые грани сходятся к этой же высоте, и заход в воду видно. Опускается только верхний слой: у воды с водой сверху высота полная, иначе в глубоком озере был бы шов на каждом слое.

Что осталось честно назвать ограничением: вода по-прежнему непрозрачная. Настоящая прозрачность требует отдельного прохода с сортировкой по глубине.

## Вода и плавание

Раньше вода была `is_collidable`, то есть по озеру можно было ходить как по стеклу. Теперь вода — жидкость:

- **Плавучесть и вязкость.** В воде гравитация слабая, а основную работу делает экспоненциальное затухание скорости (независимое от частоты кадров). Без него «плавание» означало бы просто медленное падение.
- **Скорость погружения ограничена** — как бы долго вы ни падали.
- **Вход в воду гасит падение.** Демпфирование применяется только в момент входа: постоянное превратило бы погружение в сироп.
- **Пробел удерживают, а не нажимают.** На земле прыжок срабатывает по фронту нажатия (иначе удержание давало бы автопрыжки), в воде удержание поднимает вверх с постоянной скоростью. Поэтому в физику передаются оба флага.
- Горизонтальная скорость в воде ниже, взгляд под водой получает свой туман.

**Античит пришлось учить плаванию.** Подъём в воде — это долгий набор высоты без касания земли, то есть ровно сигнатура полёта. Без этой проверки добавление воды начало бы кикать всех, кто зашёл в озеро. Решает мир, а не клиент: сервер спрашивает, есть ли вода там, где игрок себя объявил, поэтому «я плыву» посреди воздуха по-прежнему ловится. Два теста закрывают оба случая.

## Слои: сыпучее лежит восьмыми долями

Сыпучее не кладут кубометрами. Присыпка снега, нанос у стены, лопата
земли, вываленная на тропу, — всё это *часть* блока, а мир, умеющий
отвечать только «блок» и «ничего», каждую из них округляет до метра.
Округление вверх замуровывает тропу, округление вниз её теряет.

Земля, песок, снег и зола заполняют ячейку восьмыми долями. Глубина едет
в том же трёхбитном поле, в котором бревно везёт свою ось — эти два
значения взаимно исключают друг друга по построению: у наноса снега нет
оси, а бревно не бывает в восьмых долях. Поэтому ячейка по-прежнему один
`u16`, сохранение не поменяло формат, а id, записанный до появления
слоёв, читается как полный блок: ноль в этом поле означает «все восемь».

Из одной этой глубины следует всё остальное: на какой высоте стоят ноги,
сколько времени блок разбирать, во что упирается луч и рисует ли сосед
общую с ним стену.

**Экономика закрыта, и это главное решение.** Ячейка стоит один предмет —
как бы тонко материал в ней ни был размазан. Первый слой тратит предмет,
следующие слои в ту же ячейку бесплатны (материал уже оплачен, вы лишь
решаете, как его разложить), сломанная ячейка возвращает ровно один
предмет. Оплата по слою означала бы, что блок, собранный восемью
щелчками, стоит восьми предметов и возвращает один; выплата по слою
означала бы, что холм отдаёт в восемь раз больше, чем отдавал.

По умолчанию правая кнопка кладёт целый блок: стену из земли никто не
станет собирать восемью щелчками. **Alt** кладёт один слой.

Слой не висит в воздухе — ему нужен *целый* пол под собой, иначе два
мелких наноса в соседних ячейках оставили бы верхний висеть над щелью,
которую нижний не заполнил. Свет слой не задерживает, а земля под ним
остаётся освещённой.

Падающий песок доложится в неполный нанос того же материала, а не ляжет
на него сверху; что не влезло, едет в ячейку выше и ничего не теряется.

Снежники и зола так и генерируются: глубина снега растёт с высотой —
вершина завалена, граница леса припорошена, — а зола лежит тонко, потому
что это не отложение, а то, что осталось от леса.

Чего слои **не** делают: не рассыпаются вбок и не образуют откосов.
Боковая текстура слоя растянута — в вершине под текстурные координаты
отведено два бита, ровно на углы квадрата, и дробной координаты там
взяться неоткуда. На песке, земле, золе и снегу это шум по шуму, и видно
только если искать.

## Глина и гравий

Два материала, которые оставляет вода, и они берутся из одного поля шума,
прочитанного с разных концов: глина — то, что роняет стоячая вода, гравий
— то, что оставляет быстрая. Одно поле, два порога, и в одном месте их не
бывает никогда.

**Глина держит вертикальную стенку** — потому берег и берег, а не откос.
Единственный мягкий материал, сквозь который можно прокопать тоннель и не
получить обвал: слоями не лежит, не падает. Лежит у самой воды и на
плоском берегу над ней.

**Гравий сыпучий во всех смыслах**: слоями, падает, тормозит шаг — и он
единственный материал, который в основном *не он сам*. Из гравия
выветриваются желваки кремня; четыре лопаты просеиваются в один желвак.
Это способ добыть кремень там, где каменистого берега нет.

## Хитбоксы

**Столкновение доводится до касания.** Раньше заблокированный шаг просто
отменялся — приём, который прекрасно работает, пока каждая поверхность
стоит на целой высоте: игрок недоходит до неё ровно на то, что собирался
пройти за кадр, и на следующем кадре подходит ближе. С поверхностями на
восьмых долях это стало заметно: игрок висел над наносом снега на
величину, зависящую от частоты кадров, и один и тот же нанос читался
по-разному на разных машинах. Теперь ось проходится до контакта.

**Шаг.** Полметра снега, которые надо *перепрыгивать*, — не снег, а стена
по колено. Всё, что ниже половины блока, переступается на ходу; целый
блок по-прежнему стена. Шаг требует места наверху (иначе он загонял бы
голову в потолок) и того, чтобы движение наверху действительно
завершилось.

Вид догоняет ноги за десятую долю секунды, а **луч взаимодействия не
догоняет вовсе**: смещение живёт в `camera.shake`, то есть только в
матрице вида. Целиться из точки, отстающей от игрока, значит показывать
прицел не там, куда смотришь, и спорить с сервером о том, во что
щёлкнули.

**Прицельный бокс имеет форму блока.** Трава, палки и камешки жили внутри
метрового куба: рамка выделения вокруг почти пустого места и камешек,
который поднимается с расстояния в блок. Луч проверяется по коробке
самого блока, и рамка с трещинами рисуется по ней же.

Положить слой себе под ноги можно — и это самая частая постановка в игре.
Правило «в игрока строить нельзя» пропускает то, на что можно
**наступить**: физика поднимает игрока на этот слой в том же кадре, в
котором он появился. Целый блок высотой в метр по-прежнему отклоняется —
ради этого случая правило и писалось.

## Снег

По снегу идут медленнее, и чем глубже, тем медленнее. И в нём вязнут:
стоящий игрок проминает снег примерно на четверть блока, тонкая присыпка
утаптывается до земли, а сойдя со снега, игрок сразу получает высоту
обратно.

Глубина протаптывания живёт **на игроке, а не в мире**. Протоптанная
тропа означала бы правку блока на каждый шаг — сетевое сообщение и
пересборку меша на каждый шаг — ради того, что чувствует только тот, кто
в ней стоит.

## Воздух

Пятнадцать секунд под водой — переплыть озеро или нырнуть ко дну реки и
вернуться; дальше пять здоровья в секунду. Это не медленный налог на
плавание, а то, что бывает, когда не повернул назад: четыре секунды до
смерти — ровно столько, сколько нужно, чтобы всплыть с той глубины, на
которой в здравом уме плавают.

Считает **сервер**, по своей копии мира и своей копии позиции игрока — по
той же причине, по которой античит сам проверяет, есть ли вода там, где
игрок объявил, что плывёт: клиент, решающий сам, у него ли голова под
водой, никогда не утонет. Вопрос при этом тот же самый, который клиент
задаёт, чтобы нарисовать подводный туман, так что увиденное и
оплаченное — одно и то же.

Полоска воздуха появляется, только когда воздух уходит. Всегда полный
датчик — датчик, который не читают.

## Копать — это работа

Выносливость тратили бег и прыжок, а разбирать холм голыми руками можно
было бесконечно. Взмах, который что-то сломал, оплачивается по времени
работы — по тому же числу, которым отмерены полоса прогресса и трещины,
так что заплаченное совпадает с увиденным. Прерванный взмах не
оплачивается: он ничего не сдвинул.

Выдохшийся игрок копает **медленнее**, а не «не может». Невозможность
сломать блок перед собой — это способ застрять в собственной яме, из
которого нет выхода, кроме ожидания. Медленнее — честная версия
усталости, и она сама себя исправляет: вдвое медленнее копать значит
вдвое медленнее тратить.

## Песок падает

Симуляция живёт на сервере, потому что мир — серверный: клиент, считающий песок сам, разойдётся с остальными за секунду, а модифицированный клиент мог бы объявлять, что песок улёгся там, где ему удобно.

В основе — очередь координат для перепроверки, а не список объектов. Правка блока кладёт в неё ячейку и ячейку над ней; каждый такт снимается ограниченное число. Работа за такт ограничена: игрок, копающий пустыню, не остановит тик-луп — очередь просто растянется на большее число тактов.

Блок, начавший падать, **выходит из сетки мира и становится сущностью**: позиция и скорость, интегрируемые каждый такт и реплицируемые ближним клиентам, которые рисуют движение плавно между тактами. Приземлившись, он снова становится блоком. Ячейка сетки при этом пуста всю дорогу, поэтому падающий песок ничего под собой не подпирает.

**Исправлено: столб песка терял блоки.** Обрушение столба порождает по сущности на блок, они падают независимо, и нижняя приземляется в ячейку, куда направлялась следующая. Код приземления в этот момент сдавался и блок просто исчезал — подкоп под башней песка высотой в десять блоков оставлял один блок и девять несуществующих. Теперь точка покоя считается от ячейки, которая **остановила** блок (а не от той, где он оказался: под ним могли что-то построить), при занятости ищется вверх в ограниченном окне, а приземления за такт обрабатываются снизу вверх — так стопка сохраняет исходный порядок. Если места нет совсем, блок теряется, но чужую постройку не затирает.

Песок тонет в воде, вытесняя её, и не проваливается ниже y=0.

## Ёлки на севере

В тайге и тундре растут ели: ветви начинаются низко на стволе и сужаются
кверху кольцами, широкое-узкое через ряд, а не шар на голом стволе.

Это отдельная функция, а не лиственное дерево с меньшим радиусом. У
лиственного вся форма описывается шаром на конце ствола; у ели шара нет
вовсе — она шире всего внизу, сужается всю дорогу и прячет ствол. Это
разные формы, а не одна в двух размерах, и именно форма отличает холодный
лес от лиственного с той дальности, где отдельного листа уже не видно.

Тундра получила редкие ели прямо в снегу — граница леса и состоит из
последних елей перед тем, как земля сдаётся, — а на голых вершинах выше
не растёт ничего, и поэтому граница читается как граница.

## Как рисуется небо

Мир собран из кубов, а небо было единственной поверхностью вообще без
масштаба: мягкая размазня над миром из твёрдых граней — единственное, что
читалось не как погода, а как «не из этой игры».

Поле облака теперь берётся **по сетке** и держится постоянным внутри
ячейки размером примерно в дюжину блоков. Порог почти жёсткий: широкий
переход имеет смысл на гладком поле, а на сетке он всё равно попадает
внутрь одной ячейки и только делает часть пикселей полупрозрачными.
Самозатенение квантовано в три плоских тона, как тень и рисуют
пиксель-артом, плюс небольшой разброс яркости на ячейку, чтобы гряда не
была плакатно ровной.

Ветер приложен **до** привязки к сетке, а не после: по небу едет узор, а
не облака сквозь неподвижную решётку.

## Плагины и моддинг

Плагин — это папка в `plugins/` с `plugin.toml` (метаданные) и скриптом на [Rhai](https://rhai.rs):

```
plugins/
  welcome/
    plugin.toml
    main.rhai
```

**Почему скрипты, а не нативные плагины.** Нативный плагин (`.dll`/`.so`) нужно собирать тем же компилятором и с теми же версиями зависимостей, что и сервер, а любая его ошибка роняет весь сервер. Для сервера, куда люди просто кладут файлы, скрипт — правильный размен: медленнее на вызов, зато сломанный плагин — это строчка в логе, а не падение, а зациклившийся останавливается лимитом операций, а не вешает тик-луп.

**Хуки.** Скрипт определяет любое подмножество функций:

| функция | когда | `false` означает |
|---|---|---|
| `on_load()` | старт сервера | — |
| `on_join(player, name)` / `on_leave(player, name)` | подключение/отключение | — |
| `on_chat(player, text)` | сообщение в чат | отменить сообщение |
| `on_block_place(player, x, y, z, block)` | перед постановкой | отменить |
| `on_block_break(player, x, y, z)` | перед ломанием | отменить |
| `on_command(player, command, args)` | неизвестная `/команда` | «я обработал» |
| `on_tick(tick)` | раз в секунду | — |

Хуки блоков именно **отменяющие**, а не уведомляющие: плагин защиты должен успеть сказать «нет» до изменения мира, а не откатывать задним числом. Вето одного плагина достаточно — так они складываются между собой.

**Что доступно скрипту:** `broadcast`, `tell`, `log`, `set_block`, `get_block`, `block_name`, `player_position`, `player_names`, `player_count`, `time_of_day`, `set_time`, `kick` и постоянное хранилище `store` (переживает вызовы). Ни файлов, ни сети, ни процессов не зарегистрировано — плагин не дотянется до того, чего сервер ему не дал.

**Границы, которые стоит знать:**

- Мир скрипт видит как **снимок**, собранный заранее. Хук вызывается, когда сервер уже может держать блокировки мира и реестра, поэтому обращение скрипта обратно в живое состояние привело бы к взаимоблокировке тик-лупа. По той же причине действия скрипта возвращаются как данные и применяются после его завершения.
- `get_block` отдаёт только ячейки, относящиеся к событию; на остальные вернёт -1.
- Встроенные команды приоритетнее: `/players` — синоним `/list`, поэтому до плагина он не дойдёт, и подменить `/stop` нельзя.
- Неизвестный id блока в `set_block` отбрасывается на границе.
- Плагин, который валится 10 раз подряд, отключается.

В комплекте три примера: `welcome` (приветствия и своя команда `/online`), `bedrock_guard` (защита дна мира и небольшого радиуса вокруг спавна) и `daylight` (объявление заката, выключен по умолчанию — пример состояния между вызовами).

Полное руководство для авторов плагинов — в **`plugins/README.md`**: все хуки, весь доступный API, постоянное состояние и подводные камни Rhai.

## Загрузка мира

Физика игрока заморожена, пока не подгружены все 9 чанков вокруг него. Без этого игрок появлялся в пустоте и проваливался сквозь ещё не пришедший мир — а для серверного античита это выглядело как падение со скоростью 60 м/с.

На экране полоса загрузки. Шрифтового конвейера в игре нет, поэтому она нарисована геометрией на том же overlay-пайплайне, что и прицел: затемнение, рамка и растущая заливка. Этого хватает, чтобы ответить на единственный вопрос игрока — «оно зависло или работает?».

Ждём именно 3×3, а не весь радиус прорисовки: провалиться можно только в тот чанк, которого касаешься, а ожидание всего кольца держало бы игрока перед полосой загрузки ещё долго после того, как земля под ногами стала твёрдой.

## Постройка внутри игроков

Ставить блок внутрь игрока нельзя — включая себя самого. Основной случай именно последний: посмотреть под ноги и щёлкнуть правой кнопкой означало бы замуровать себя в землю.

Геометрия коллайдера вынесена в общий крейт (`primitive_shared::geometry`), чтобы клиент и сервер не разошлись в том, что считается «внутри игрока»: две копии константы «какой ширины игрок», разъехавшиеся на 0.05, дали бы клиенту предсказание, которое сервер отвергает, и для игрока это выглядело бы как случайные лаги.

Клиент отсекает такую постановку локально — блок даже не мигнёт. Сервер проверяет то же самое авторитативно, потому что модифицированный клиент иначе мог бы замуровать соседа.

Касание не считается пересечением: блок, на котором стоишь, и стена, к которой прижался, остаются доступными для постройки.

## Текстуры граней

`assets/textures/blocks.toml` принимает две формы:

```toml
stone = "stone.png"                                   # одинаково на всех 6 гранях
grass = { top = "grass_top.png", side = "grass_side.png", bottom = "dirt.png" }
log   = { top = "log_top.png", bottom = "log_top.png", side = "log_side.png" }
```

Ключи граней: `top`, `bottom`, `side` (все четыре боковые сразу), `north`, `south`, `east`, `west` и `all` как запасной вариант. Порядок разрешения: собственное имя грани → `side` → `all` → заглушка. Блоку с одной особенной гранью не нужно перечислять все шесть.

Одинаковые файлы загружаются один раз и переиспользуются: низ травы и обычная земля делят слой. Для 10 блоков это 14 слоёв вместо 60 при наивной реализации. Опечатка в имени грани — явная ошибка при разборе, а не молчаливая заглушка без объяснений.

Старый формат (одна строка на блок) продолжает работать без изменений.

## Команды сервера

Один парсер и один диспетчер на два источника: stdin сервера (права оператора) и сообщение в чате, начинающееся с `/` (права игрока). Так команда не может существовать для одного источника и отсутствовать у другого, а права проверяются ровно в одном месте.

```
/help /list /where /spawn /stats /time              — доступно игрокам
/time <0..1|day|night|noon|midnight> /tp /say
/save /kick /op /deop /stop                          — только оператору
```

Оператор — это флаг в профиле игрока (`players.bin`), а не список в
отдельном файле: права — такой же факт об игроке, как его рюкзак, и
хранятся под тем же UUID, в том же хранилище, которое уже загружается до
первого подключения и атомарно сохраняется. `/op` работает и по офлайн-
игроку, но только по знакомому серверу имени; права появляются со
следующей же введённой строки, без переподключения. Консоль — оператор по
определению, и `deop` её не касается.

Ведущий `/` необязателен, так что в консоли работает и `list`, и `/list`. `/time` понимает как долю 0..1, так и названия фаз — «0.75» не то, как человек думает о закате. Разбор отделён от исполнения: `parse` — чистая функция над строкой, поэтому неизвестные команды, нехватка аргументов, кривые числа и уровни прав тестируются без запущенного сервера, сокета и мира.

## Античит

Ключевое решение: **бюджет расстояния, а не мгновенная скорость**. Наивная проверка `расстояние / dt` даёт ложные срабатывания после сетевого затыка, когда приходит несколько апдейтов подряд с крошечным dt. Здесь — token bucket, пополняющийся с легальной скоростью: всплеск после лага переживается, устойчивое превышение режется.

Проверяется: NaN и бесконечности, границы мира, телепорт, вертикальная скорость, горизонтальный бюджет, полёт (накопленный подъём без касания земли), зависание, ложный «стою на земле» (сверяется с реальным блоком под ногами), дальность взаимодействия (от последней известной серверу позиции глаз), валидность id блока, дальность запроса чанка и пять рейт-лимитов.

Нарушения копят очки с **затуханием во времени** — один лаг-спайк никогда не приводит к кику, систематический чит приводит. Порог и веса настраиваются в `[anticheat]`.

Проверено на практике: первая версия `verify_broadcast` ставила блок в 10 блоках от спавна, не сообщив серверу о перемещении — сервер отказал, `anticheat_flags=1`. Это ровно сигнатура reach-хака. Пример исправлен так, чтобы вести себя как настоящий клиент.

Он же поймал вторую сигнатуру и третью, уже своим переписыванием: телепорт (пройти двадцать блоков одним сообщением) и падение (спуск с холма, объявленный как полёт вниз, — это падение с девятнадцати блоков, и игрок приходит на место мёртвым). Обе — не придирки античита, а ровно то, что он должен ловить; пример теперь идёт шагами и по земле.

## Сущности

Падающий песок больше не телепортируется по клеткам — он становится **сущностью**: позиция и скорость, интегрируемые каждый такт, реплицируемые ближним клиентам, с интерполяцией между тактами на клиенте. Приземлившись, снова становится блоком.

Прежний вариант сдвигал блок на клетку раз в несколько тактов. Это читалось как рывки, и всё это время блок занимал клетку в сетке, то есть мешал тому, что под ним. У сущности нет ни того, ни другого: клетка пуста, пока блок в воздухе.

Детали, которые пришлось обдумать:

- **Шаг за такт ограничен.** Без этого блок, падающий с высоты, за один такт проскакивает пол насквозь и продолжает лететь. Тест с заведомо огромным шагом (0.5 с — такой даёт подвисший сервер) это фиксирует.
- **Приземление в свою клетку, а не на клетку выше.** Первая версия ставила блок на клетку выше, и он оставался висеть над землёй. Поймано тестом.
- **Нет сообщения о деспавне.** Клиент выбрасывает сущность, о которой перестал слышать. Потерянный деспавн не может оставить вечного призрака — худшее, что бывает, это лишняя доля секунды.
- **Отрисовка через конвейер местности.** Сущность — это куб в мировых координатах в том же формате вершин, что и блоки, поэтому она получает те же текстуры, освещение и туман без второго конвейера.

## Дыры при удалении блока

Это была гонка, которую я сам внёс вместе с многопоточным мешингом: две задачи на один чанк могут выполняться одновременно и завершиться в любом порядке. Меш, построенный **до** правки, мог прийти **после** меша, построенного с правкой, и затереть его — блок возвращался на место, либо у соседних блоков не было новых открывшихся граней, и это выглядело как дыра.

Теперь у каждого чанка есть счётчик правок. Он уезжает с задачей и возвращается с результатом; устаревший результат выбрасывается, а чанк ставится в очередь заново. Счётчик отброшенных мешей виден в F3 (`stale_meshes`).

## Зависания

Причина была конкретная: клиент разбирал очередь сообщений целиком за один кадр (`while let Ok(msg) = try_recv()`), а каждый пришедший чанк тут же **освещался** — обход 256 колонок плюс заливка. Сервер шлёт несколько чанков за тик, поэтому после любой заминки в канале лежала пачка, и она интегрировалась в одном кадре: сотни миллисекунд, в которые игра просто не отвечала.

Теперь приём и интеграция разделены. Сокет вычитывается жадно (сервер никогда не видит зависшего читателя), а интеграция идёт по бюджету времени на кадр.

Первая версия этого разделения породила вторую ошибку, которую видно было только вживую: чанк, лежащий в очереди, не считался загруженным, логика повторных запросов просила его снова, сервер снова присылал — и очередь кормила сама себя. На области в 169 чанков накопилось 853 записи в очереди. Пришедшие чанки теперь отмечаются сразу, ещё до интеграции.

И сама интеграция была слишком дорогой: BFS шёл по карте чанков с хеш-поиском на каждое посещение ячейки — около 130 мс на чанк в отладочной сборке, то есть один чанк выносил весь бюджет. Теперь чанк сначала освещается **изолированно в локальном массиве** (обычная индексация, никаких хешей), а по карте согласуются только четыре шва, и только те ячейки, где стороны расходятся больше чем на уровень. Стало ~17 мс на чанк.

Замерено вживую: `chunk_time/s` 663 мс → 85 мс, очередь прибытий 853 → 0.

## Все ядра

Пул рабочих потоков теперь берёт **все ядра, кроме одного** (основной поток продолжает рисовать, считать физику и обслуживать сеть) — раньше стоял потолок в 4. Потолок ставился из осторожности к простаивающим потокам, держащим буферы; вместо него теперь ограничены сами пулы (на поток), что и есть прямое решение той проблемы. Число потоков настраивается: `worker_threads` в `client_settings.toml`, 0 = решать автоматически.

На эти же потоки уехало **освещение чанков**. Оно распадается на чистую половину (осветить чанк изолированно — дорого, ни с чем не разделяется) и половину, трогающую общую карту (согласование швов — дёшево). Первая ушла в воркеры, вторая осталась на владеющем потоке. В основном потоке от интеграции чанка осталось только копирование блоков.

Сервер уже был многопоточным: tokio по умолчанию использует все ядра, генерация рельефа идёт через `spawn_blocking`, мир разбит на 32 шарда с раздельными блокировками.

Замерено вживую (та же сцена, 169 чанков, установившийся режим): кадр **132 мс → 89 мс**, p99 **165 мс → 112 мс**. И это на одном ядре в песочнице — выигрыш здесь только от того, что основной поток больше не мешает и не освещает вовсе; на реальной машине к этому добавится параллелизм.

## Построение мешей в фоновых потоках

Построение меша чанка стоит ~14 мс в отладочной сборке и раньше шло в основном потоке под бюджетом в 4 мс. Бюджет этого не мог удержать: проверка происходит **между** чанками, поэтому один чанк пробивал её насквозь. Отсюда ровно тот симптом, о котором вы писали, — время кадра скачет в зависимости от того, попал ли в кадр мешинг.

Из-за этого же ломание блока выглядело сломанным: правка помечала чанк грязным, чанк уходил в конец очереди, которая при подгрузке местности бывала на сотню записей, и перестроение приходило через секунды.

Теперь работа разделена. Основной поток делает дешёвое: заполняет `Neighbourhood` (324 обращения по колонкам — чанк плюс блок паддинга, блоки и свет). Рабочие потоки делают дорогое: обходят полмиллиона ячеек, собирая грани, свет и AO. Буферы (~60 КБ окрестность и вершинные буферы) ездят туда и обратно и складываются в пул — в установившемся режиме на чанк не аллоцируется ничего.

**Очередь приоритетная.** Правки игрока подаются раньше потоковой подгрузки: чанк, который игрок только что изменил, — это тот, на который он смотрит. Тест это фиксирует: при 59 чанках обычной очереди отредактированный чанк уходит в работу первым.

Замерено вживую: затраты основного потока на мешинг 123 мс/с → 67 мс/с, а в покое 0. (В песочнице одно ядро, поэтому рабочий поток всего один — на реальной машине их до четырёх.)

## Что и сколько стоит

Замер живёт в крейте, не в предположениях:

```bash
cargo test --release -p primitive_client --bin primitive_client -- --ignored --nocapture bench
```

Не `#[bench]` (нужен nightly) и не criterion (целый крейт ради кода, у
которого и так есть бюджет в миллисекундах в кадровом цикле). Сборка
обязательно релизная: в debug эти стадии в десять–двадцать раз медленнее
и соотношения между ними другие, так что debug-числа не говорят ничего о
том, что чувствует игрок.

Чанк для замера выглядит как место, где действительно можно стоять:
поверхность, пруд, пещеры, два дерева. Форма важна — сплошной куб почти
не даёт граней, шахматка даёт максимум, и ни то ни другое не измеряет
ничего.

На момент 1.4.0 (на машине, где мерялось всё остальное в этом разделе):
освещение 0.17 мс, заполнение окрестности 0.09 мс (единственная стадия в
главном потоке), построение меша 0.88 мс.

Тем же прогоном меряется и физика — то, что главный поток платит каждый
кадр по нескольку раз: луч взаимодействия 0.21 мкс на бросок и полный шаг
столкновений 0.40 мкс. Абсолютные величины тут маленькие; смысл в том,
что они меряются, а не в том, что они малы.

### Мешер шагает, а не считает индекс

Выборок из окрестности — сотни тысяч на чанк, и каждая стоила умножения,
сложения и четырёх сравнений с границами. Теперь шаг — сложение с
постоянным смещением от индекса текущей ячейки.

Горизонтальные проверки границ не потеряны, а доказаны лишними. Любая
выборка мешера отстоит от обрабатываемой ячейки не более чем на один шаг
по каждой оси: грань смотрит на один шаг вдоль нормали, а углы AO
смещаются на шаг вдоль двух *перпендикулярных* осей — то есть суммарное
смещение по любой одной оси не больше единицы. При x и z в 0..15 и
паддинге в единицу `x + dx` всегда попадает в −1..16, ровно в паддинг.
Проверять надо только y: у мира есть верх и низ, и паддинга для них нет.

Общий `block` остался для мест, где это рассуждение не работает.

### Покадровая геометрия в постоянных буферах

Падающие блоки и другие игроки перестраиваются каждый кадр, потому что
каждый кадр двигаются. Загружать их как обычный меш означало создавать
два буфера GPU на меш на кадр — при 60 fps больше двухсот аллокаций в
секунду под данные, размер которых почти не меняется. Буферы теперь живут
между кадрами, растут до следующей степени двойки и не сжимаются:
следующему кадру обычно нужно столько же места.

## Оптимизация

- **Пустые чанки не мешатся.** Над поверхностью большинство чанков — чистое небо; просмотр 16 тыс. ячеек, чтобы это понять, куда дешевле обхода в полмиллиона, который всё равно ничего не выдаст.
- **Отсечение по пирамиде видимости.** Раньше draw call выдавался на каждый загруженный чанк — 289 при радиусе 8, из которых при поле зрения 70° видна хорошо если треть. Плоскости пирамиды извлекаются прямо из матрицы вида-проекции, так что дополнительное состояние не нужно. Замерено в живом прогоне: 51 draw call вместо ~150, отсекается 92–98 чанков.
- **Кэш окрестности при построении меша.** Чтение соседних блоков напрямую из мира означало хеш-поиск чанка на каждую ячейку, а мешер трогает порядка 500 тыс. ячеек на чанк (6 граней × 4 угла × 3 соседа для AO плюс отсечение граней). Это давало ~26 мс на чанк и выносило бюджет кадра. Заполнение кэша — 324 поиска (по одному на колонку, а не на ячейку), дальше всё индексация массива. Замерено: **390 мс/с → 123 мс/с**.
- **Один и тот же промах трижды: хеш-поиск на ячейку вместо поиска на чанк.** Копирование блоков чанка (16 384 поиска), согласование швов освещения (~16 000) и заполнение окрестности для мешера (20 736). Клиент теперь клонирует блоки прямо из пришедшего чанка, шов берёт данные обеих сторон по разу, окрестность — по разу на колонку. Замерено: интеграция чанка **456 → ~2 мс/с**, швы **899 → ~200 мс/с**, подготовка меша **10 → 3 мс на чанк**. FPS во время подгрузки: **14–21 → 21–27**.
- **Чанк ждёт соседей перед мешингом.** Меш зависит от восьми соседей, поэтому мешить чанк до их прихода — значит мешить его заново на каждого; при стриминге 169 чанков это превращало ~169 задач в больше тысячи. Крайнее кольцо не ждёт вечно: сосед за пределами радиуса прорисовки считается «уже не придёт».
- **Отсечение по туману.** Загруженная область — квадрат, а видно по кругу: при дальности 16 углы уходят на 360 блоков при конце тумана в 240, и эта треть чанков рисовалась впустую. За концом тумана шейдер уже подмешал цвет тумана целиком, а буфер очищен ровно в этот цвет — и небо у горизонта приходит в него же (за этим оно и сделано). Значит, чанк за этой чертой не меняет ни одного пикселя. Замерено: **584 draw call → ~480**, ожидание GPU **0.97 → 0.71 мс**, кадр **1.6 → 1.2 мс** при дальности 16; при дальности 8 кадр **0.8 → 0.55 мс**. Выключается вместе с туманом (тогда предела видимости нет) и под водой — там террейн уходит в цвет тумана, а небо в 55% от него, и разница читалась бы тёмной полосой.
- **Небо считает облака в два шага.** Проход неба выполняется для каждого пикселя, который не закрыл мир, поэтому шесть выборок шума там стоят измеримо. Искажение формы облака взято одной октавой вместо четырёх (через порог разницы не видно: смещение меньше ширины среза), а самозатенение — вторая четырёхоктавная выборка — считается только там, где облако вообще есть. Треть стоимости прохода.
- **Листва освещается плоско.** Плавное освещение и AO стоят восемнадцати выборок на грань и окупаются на стенах с углами; у кроны нет ни того ни другого, а граней у неё больше, чем у всего остального — дерево это сотни граней там, где обрыв десяток. Грань листвы берёт свет ячейки перед собой и никакого затенения: одна выборка вместо восемнадцати. Замерено: **0.88 → 0.82 мс на чанк** на сцене с двумя деревьями, и выигрыш растёт с долей листвы. Заодно выглядит лучше — у кроны, затенённой по углам, видна решётка.
- **Листва и трава уходят одним вызовом.** Они делят конвейер и лежат в соседних диапазонах индексов, так что чанк, попадающий в обе дистанции, рисуется одним `draw_indexed` вместо двух — вблизи игрока это половина cutout-вызовов кадра.
- **Кэш перекрытия в мешере.** Отсечение граней и AO спрашивают о девяти ячейках вокруг каждой грани, шесть граней на блок, и каждый вопрос выполнял `is_opaque` — пять предикатов со снятием полей id. Теперь это один байт, и в нём же лежит глубина слоя, которая нужна отсечению. Замерено: **1.22 → 0.91 мс на чанк** — в рабочем потоке.

  Байт берётся из **таблицы**, а не из третьего массива в окрестности. Массивом он был одну версию и стоил 16 384 лишних записи на чанк в *главном* потоке: заполнение окрестности выросло с 0.042 до 0.091 мс, а это единственная стадия, которую игрок чувствует напрямую — она идёт в кадровом цикле, пока стримится местность, и на высокой частоте кадров это сотни fps. Id блока это шестнадцать бит, все возможные ответы влезают в 64 КБ, считаются один раз и читаются по индексу; заполнение вернулось к **0.053 мс**.
- **Луч идёт по ячейкам, а не выборкой каждые пять сантиметров.** Шесть блоков дальности — это 120 хеш-поисков чанка на луч, и лучей три на кадр (ломание, постановка, проверка удара сквозь стену), против десятка ячеек, которые луч действительно пересекает. Замерено: **1.00 → 0.21 мкс на луч**. Заодно исчезла неточность: ячейка постановки теперь настоящий сосед по пересечённой грани, а не «где оказалась предыдущая выборка».
- **Столкновение читает мир колонками**, а не ячейками: коллайдер игрока задевает четыре колонки и три ячейки по высоте, то есть двенадцать хешей за ответ, который лежит в четырёх чанках.
- **Инкрементальный свет** вместо девяти полных пересчётов на клик (см. выше).
- **Переиспользуемые буферы** мешинга вместо двух свежих `Vec` на чанк на кадр.
- **Бюджет мешинга во времени**, а не в числе чанков: пустой небесный чанк и система пещер отличаются на порядок.
- **Упаковка света в полубайты** — 16 КБ на чанк вместо 32 КБ, и оба канала ячейки в одной кэш-линии.

Замечание про цифры FPS ниже: все замеры сделаны в отладочной сборке на программной растеризации (llvmpipe), поэтому абсолютные значения ни о чём не говорят. Осмысленно только сравнение «до/после» в одинаковых условиях.

## Интерес: сетка вместо перебора

Сборка снапшотов была единственным местом в сервере, которое росло как
квадрат числа игроков: каждый сравнивался с каждым, каждый такт. Проверка
расстояния — три вычитания и скалярное произведение, поэтому долго это
оставалось дёшево, а потом перестало: при 256 игроках это 65 000 сравнений
двадцать раз в секунду, и почти все — между людьми, которые друг друга и
так не видят.

Теперь позиции раскладываются в равномерную сетку по x/z с ячейкой в
радиус интереса, и запрос читает блок 3×3 вокруг спрашивающего. Стоимость
становится пропорциональна тому, сколько игроков рядом на самом деле, —
ровно то, ради чего радиус интереса и вводился.

Чего сетка намеренно **не** делает. Она не разбивает по вертикали: мир
высотой 64 блока при радиусе 160 уложился бы в один слой, и ось стоила бы
измерения бухгалтерии впустую. Проверка расстояния при этом осталась
полностью трёхмерной — сетка только решает, кого стоит проверять. И она
строится заново каждый такт, а не поддерживается инкрементально: игроки
двигаются непрерывно, так что инкрементальная версия делала бы ту же
работу, но труднее для чтения.

Тест сверяет её ответы с прежним линейным перебором — на отрицательных
координатах, на швах ячеек и на границе радиуса. Это оптимизация, поэтому
любое расхождение — её баг.

## Готовность к большому онлайну

- **Шардированные локи** — 32 шарда по пространственному хешу вместо одного глобального мьютекса на весь мир.
- **Правки живут в разреженном оверлее**, а не в чанке. Так как генерация детерминирована, чанк можно выселить из кэша и пересоздать байт-в-байт. Память ограничена `max_cached_chunks`, а не объёмом исследованного мира.
- **Снапшоты по тику с фильтрацией по радиусу интереса** — O(соседей) на игрока, а не O(всех игроков). Раньше движение ретранслировалось сообщение-в-сообщение.
- **Обратный индекс «чанк → подписчики»** для рассылки правок блоков.
- **Ограниченные очереди с явной политикой отбрасывания** вместо unbounded: медленный клиент отключается, а не съедает память сервера.
- Три задачи на клиента (чтение / запись / подкачка чанков), генерация рельефа в `spawn_blocking`.
- Keepalive и таймауты, лимит соединений с одного IP, автосохранение, метрики, корректное завершение по Ctrl-C с рассылкой уведомления и сохранением мира.

- `cargo test --workspace` — **895 тестов** (487 клиент + 8 шейдерных, 167 + 28 сервер, 205 общий крейт).
- Шейдеры компилируются и проходят проверку типов через naga в составе обычных тестов.
- `verify_broadcast` против живого сервера: рукопожатие, стриминг чанков, **игрок доходит до блока пешком**, ломает его, и правку видят оба клиента; выпавшее подбирается с земли и приходит в инвентаре; постройка внутрь себя отклоняется; **слой кладётся, догружается вторым слоем бесплатно и суммарно стоит один предмет** — вся экономика слоёв по проводу; часы мира идут, `/list` из чата отвечает, `/stop` от обычного игрока отклоняется по правам, **плагин отвечает на придуманную им команду и накладывает вето на правку блока**.

  Пример пришлось чинить: он ставил блок из воздуха, а инвентарь давно серверный — placement отклонялся с «you are not carrying that», и единственным симптомом было то, что проверка молча висела. Теперь он добывает блок так же, как игрок (сломать, подойти, поднять), ходит шагами вместо телепорта, печатает любой отказ сервера вслух и ограничивает ожидание целиком, а не каждое сообщение по отдельности: висящая проверка — это проверка, которая ничего не проверяет.
- Команды консоли прогнаны вживую: `help`, `list`, `time`, `time night`, `stats`, `save` — все отвечают корректно.
- Реальный запуск под Xvfb с программным Vulkan (llvmpipe): окно открывается, текстуры грузятся, 169 чанков прогружаются и мешатся, отсечение работает, на снятых кадрах видны туман, освещение, разные текстуры верха и боков травы, дневной и ночной кадры.
- **Два клиента одновременно** видят друг друга.
- Полный путь под Xvfb с эмуляцией клавиатуры и мыши: экран выбора сервера → Enter → подключение → загрузка мира → захват курсора → взгляд вниз → ломание блока. На снятом кадре — аккуратная яма со стенками и дном, а не дыра в пустоту.
- Сняты кадры: экран загрузки с полосой на 2/9 чанков, ночная сцена с хотбаром и корректно ориентированной боковой текстурой травы.

### Про замеры частоты кадров

Все прогоны — отладочная сборка на программной растеризации (llvmpipe). При установившемся состоянии кадр занимает ~132 мс, из которых на наш код (построение мешей) приходится ~14 мс; остальные ~118 мс — программный растеризатор. То есть сравнивать осмысленно только «до/после» внутри одинаковых условий, а абсолютные значения не говорят ни о чём. Отдельно: счётчик кадрового времени раньше писал *обрезанный* шаг физики, из-за чего любой медленный кадр показывался ровно как 100 мс и скрывал реальную картину — теперь пишется настоящее время кадра.

## Известные ограничения

- Отсечения по перекрытию (occlusion culling) нет: под землёй рисуется много того, что закрыто камнем.
- Свет пересчитывается только на клиенте. Для серверных механик (мобы, рост растений) его пришлось бы считать и на сервере.
- Вода не течёт: это статичный объём, а не симуляция потока. Сломанный блок под водой не заполняется. Правила уровня и растекания уже лежат в `primitive_shared::fluid` — не хватает самой симуляции.
- Прозрачность воды сортируется по чанкам, а не по граням: две поверхности воды внутри одного чанка на разной глубине могут наложиться не в том порядке.
- Ныряльщик задерживает дыхание пятнадцать секунд; полоска воздуха появляется, только когда он кончается.
- Песок не рассыпается вбок и не образует откосов — падает строго вниз, хотя и умеет доложиться в неполный нанос под собой.
- Боковая текстура слоя растянута по высоте: в вершине под текстурные координаты отведено два бита, ровно на углы квадрата.
- Гравитации подвержены песок и гравий; земля, снег и зола лежат слоями, но не падают — их держит проверка опоры, а не симуляция. Земля, снег и зола лежат слоями, но не падают — их держит проверка опоры, а не симуляция.
- Падающие блоки не сохраняются: остановка сервера в момент падения теряет то, что было в воздухе.
- Плагины не могут добавлять свои блоки или предметы — только реагировать на события и менять мир существующими блоками.
- Плагины не перезагружаются на лету: изменения подхватываются при перезапуске сервера.
- Сущности пока только одного вида — падающий блок. Мобов и предметов нет.
- Мир нельзя переименовать после создания — только создать заново.
- Шрифт покрывает печатный ASCII; кириллица в интерфейсе отрисуется рамками.
- Фон меню — плитка одной текстуры, а не сцена: это обои, а не мир за спиной.
- Чат виден только в консоли: поля ввода чата в игре нет.

### Куда это подключать

Под следующее обновление уже вкопаны два места, и оба выбраны так, чтобы
новая механика была *реализацией*, а не ещё одной веткой в тик-лупе.

**Вода.** `primitive_shared::fluid` описывает воду как уровень в восьмых
долях: высоту поверхности (её уже читает мешер), шаг растекания и чистую
функцию `settle` — вниз, потом вбок, и только в то, что ниже. Правила
приехали в общий крейт **раньше** симуляции нарочно: разойтись клиенту и
серверу в том, где поверхность воды, — ровно тот класс ошибок, ради
которого этот крейт и существует, и он выглядит как стена воды не там,
где она нарисована. Уровень едет в том же поле, что и глубина слоя, так
что формат ячейки менять не придётся.

**Механики.** `primitive_server::logic::simulation` — форма, по которой
пишется всё, что следит за ячейками: очередь координат, бюджет работы на
такт и изменения, возвращаемые данными (рассылку и то, что ещё должно
случиться с изменённой ячейкой, знает вызывающий). Падающий песок
реализует этот трейт без единой правки — форма с него и снята. Текущая
вода, огонь, зарастание травой и рост посевов — это `CellMechanic` и
вызов `register`.

Два правила, которые там записаны, стоит прочитать до того, как писать
третью механику: `on_block_changed` — уведомление, а не работа (его
зовут с игрокового соединения, под замками), и `step` обязан уложиться в
выданный бюджет (игрок, выкапывающий пустыню, ставит в очередь тысячи
ячеек, и такт, который вычерпает их все, — это такт длиной в секунду).

## Вес сборки

Клиент — около 7 МБ, сервер — около 2.7 МБ. Почти всё это wgpu, naga и
winit; убрать их можно только вместе с рендером.

Что сделано и что это дало:

- **Профиль релиза**: fat LTO, один codegen unit, `panic = "abort"`,
  снятые символы.
- **`opt-level = "s"` для крейтов, работающих только на старте** —
  `naga`, `image`, `toml`, `winit`. Ни один из них не находится в кадре:
  шейдеры компилируются один раз, четырнадцать PNG 16×16 декодируются
  один раз, конфиги читаются один раз. Всё горячее — мешер, заливка
  света, `glam`, покадровое кодирование wgpu — остаётся на `opt-level = 3`.
  Это дало примерно 0.2 МБ.
- **Набор фич tokio** сужен с `full` до восьми используемых. На размер
  это не повлияло: fat LTO уже выбрасывал остальное. Выигрыш — время
  сборки и то, что список зависимостей теперь не врёт (149 → 120
  крейтов).

Чего сознательно **не** сделано: `opt-level = "s"` или `"z"` для всего.
Это уменьшило бы бинарник заметнее и замедлило бы построение мешей и
освещение — то есть ровно то, от чего зависит частота кадров.

## Про Cargo.lock

Отслеживается намеренно (это workspace бинарников). Несколько транзитивных зависимостей закреплены на чуть более старых версиях — это требование старого тулчейна 1.75 в песочнице разработки, а не кода. На современном тулчейне `cargo update` спокойно их поднимет.
