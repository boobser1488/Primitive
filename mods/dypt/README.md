# dypt внутри игры

Мод, который приводит в игру язык программирования **dypt** — и делает
на нём возможными две вещи.

**Выполнить что-нибудь прямо сейчас:** `/dypt дом.dpt` — и дом
строится. Принимаются все три вида входа языка: исходник `.dpt`,
байткод `.dyc` и его дизассемблированная запись `.dasm`.

**Написать мод без сборки:** файл в `mods/dypt/mods/` объявляет
`on_break`, `on_chat`, `on_tick` — и игра зовёт их, когда это
происходит. Правка становится живой по `/dypt reload`: без
`cargo build`, без перезапуска сервера.

И тому и другому доступна игра: 132 функции поверх всех таблиц API —
блоки, игроки, животные, вещи, свет, вода, огонь, печи, рецепты, — и
`command()` там, где отдельной функции нет.

```dypt
// scripts/tower.dpt
где = pos()
основание = surface(где[0], где[2])
i = 0
while i < 8 {
    place(где[0] + 3, основание + 1 + i, где[2], "stone")
    i = i + 1
}
print("готово")
```

## Моды на dypt, без сборки

Файл в `mods/dypt/mods/` — это мод. Он загружается при старте сервера,
живёт постоянно и ловит события: объявите функцию с оговорённым именем,
и игра будет её звать.

```dypt
// mods/dypt/mods/bedrock.dpt — весь мод целиком
function on_break(игрок, x, y, z, блок) {
    if block_name(блок) == "bedrock" {
        tell(игрок, "бедрок не ломается")
        return false
    }
    return true
}
```

Правка становится живой по `/dypt reload` — без `cargo build`, без
перезапуска сервера.

Состояние живёт между событиями: переменная верхнего уровня — это
память мода.

```dypt
всего = 0
function on_join(игрок, имя) {
    всего = всего + 1
    say(имя + " пришёл (" + всего + "-й)")
}
```

Скриптовому моду доступен тот же словарь из 132 функций, что и разовому
скрипту, и `print` у него уходит в журнал сервера под именем файла.

### Обработчики

Отменяемые помечены: `false` из такого обработчика означает «не давать».
У всех остальных возвращённое значение ни на что не влияет — в том числе
`null`, который возвращает функция без `return`, так что забыть его
безопасно.

| функция | когда | отмена |
|---|---|:--:|
| `on_load()` | мод загрузился (и при каждом `/dypt reload`) | |
| `on_unload()` | мод выгружается: остановка сервера или `reload` | |
| `on_start()` | сервер поднялся | |
| `on_stop()` | сервер останавливается | |
| `on_tick(такт)` | каждый такт — двадцать раз в секунду | |
| `on_join(игрок, имя)` / `on_leave(игрок, имя)` | пришёл, ушёл | |
| `on_chat(игрок, текст)` | сказал в чат | **да** |
| `on_command(игрок, имя, доводы)` | неизвестная серверная команда; `true` означает «я это сделал» | — |
| `on_death(игрок, отчего)` | умер | |
| `on_hurt(игрок, сколько, отчего)` | получает урон | **да** |
| `on_healed(игрок, сколько)` | подлечился | |
| `on_ate(игрок, блок, слот)` | ест | **да** |
| `on_drank(игрок)` | пьёт | |
| `on_water_in/out(игрок, x, y, z)` | голова ушла под воду и обратно | |
| `on_slot(игрок, слот, блок)` | сменил вещь в руке | |
| `on_place(игрок, x, y, z, блок)` | ставит блок | **да** |
| `on_break(игрок, x, y, z, блок)` | ломает блок | **да** |
| `on_changed(x, y, z, блок)` | ячейку изменило что угодно: вода, песок, огонь, мод | |
| `on_tree(игрок, x, y, z, сколько)` | валит дерево | **да** |
| `on_chunk(x, z)` | сгенерирован чанк (**из потока генератора**, часто) | |
| `on_spawn(существо, x, y, z)` / `on_gone(существо)` | завелось, исчезло | |
| `on_craft(игрок, блок, сколько, рецепт)` | мастерит | **да** |
| `on_pickup(игрок, блок, сколько, x, y, z)` | поднял с земли | |
| `on_dropped(игрок, блок, сколько)` | выбросил | **да** |
| `on_tool_broke(игрок, блок, слот)` | инструмент сломался в руках | |
| `on_cured(игрок, x, y, z)` | шкура довялилась | |
| `on_equip(игрок, блок, слот)` | надел или снял | |
| `on_open(игрок, x, y, z, блок)` | открыл сундук — отмена работает как замок | **да** |
| `on_close(игрок, x, y, z)` | закрыл | |
| `on_smelted(x, y, z)` | печь довела дело до конца | |
| `on_growth(x, y, z, блок)` | что-то выросло | |
| `on_fire_out(x, y, z, блок)` | огонь погас | |
| `on_weather(погода)` | сменилась погода | |
| `on_time(время)` | время суток **переставили** (не «идёт») | |

Подписка идёт только на то, у чего есть обработчик: скрипт без
`on_changed` не стоит игре ничего на каждой ячейке, которую сдвинула
вода.

### Как это работает и где у этого края

Все живые скрипты принадлежат одному потоку — окружение языка держится
на `Rc` и между потоками не ходит. Обработчик события в игре кладёт
вызов в очередь этого потока и **ждёт ответа**: у отменяемого события
ответ нужен до того, как действие состоится.

Отсюда три правила, и каждое стоит знать до того, как оно удивит.

**Обработчик обязан быть быстрым.** Пока он считает, стоит такт
сервера. Долгую работу разовым скриптом (`/dypt файл`) — он идёт на
своём потоке и такт не держит.

Замерено на пустом мире, три окна подряд:

| | tps |
|---|---|
| как поставляется (такт никто не ловит) | 19.7 / 19.9 / 19.9 |
| один скрипт с пустым `on_tick` | 18.7 / 18.8 / 17.6 |

Полтора такта в секунду — это цена не самого обработчика (он пустой), а
перехода в чужой поток и обратно двадцать раз в секунду. В `busy
ms/tick` она не видна, потому что такт не считает, а **ждёт**. Отсюда
правило: `on_tick` берут, когда действительно нужен каждый такт;
«раз в секунду» дешевле сделать внутри него счётчиком.

**Зависший обработчик отключает доставку.** Через `handler_ms` (по
умолчанию секунда) мод объявляет поток скриптов потерянным и перестаёт
слать в него события, о чём пишет в журнал. `/dypt reload` бросает
зависший поток и заводит новый — брошенный останется жечь одно ядро до
перезапуска сервера, потому что прервать чужой поток нечем ни в Rust,
ни в dypt.

**События, которые скрипт вызвал сам, ему не приходят.** Обработчик,
поставивший блок, не получит на него `on_changed`: иначе он ждал бы
самого себя. Это же отсекает вечную рекурсию «поставил — услышал —
поставил».

Ещё три мелочи:

* Скриптовый мод — всегда `.dpt`. `.dyc` и `.dasm` бывают только у
  `/dypt файл`: они выполняются байткодовой VM, а обработчики зовёт
  AST-интерпретатор, которому нужно дерево.
* Обработчик не может быть `async`.
* Порядок загрузки — по алфавиту, и он решает, чей `on_break` скажет
  «нет» первым. Спрашивают всех: скрипт, который считает сломанные
  блоки, досчитает, даже если сосед уже отказал.

## Что нужно, чтобы это заработало

Три шага, все обязательны.

**1. Собрать мост со стороны языка.** Он лежит в репозитории dypt, в
папке `embed`:

```bash
cd C:/projects/rust/dypt/embed
cargo build --release
```

Получится `embed/target/release/dypt_embed.dll`. Положите её рядом с
`mod.ron` — то есть в `mods/dypt/`.

**2. Собрать сам мод** (он в рабочем пространстве игры):

```bash
cargo build -p dypt --release
copy target\release\dypt.dll mods\dypt\
```

**3. Запустить игру.** Одиночный мир грузит моды так же, как
выделенный сервер, и единственный игрок в нём — оператор:

```bash
cargo build --release -p primitive_client
target\release\primitive_client.exe
```

В окне, из которого запущена игра, должно появиться:

```text
[mods] loaded mod 'dypt' 1.0.0 (API 2.0)
[mod] dypt 1.0.0 готов: 132 игровых функций, скрипты в ...\mods\dypt\scripts
```

Дальше — просто откройте мир и наберите в чате `/dypt list`.

На выделенном сервере всё то же самое; `target\release\primitive_server.exe`,
и клиент подключается к `127.0.0.1:7878`. Разница одна: там оператора
назначают, а в своём мире им становятся сами.

### Куда именно класть файлы

Туда, откуда сервер **на самом деле** взял `dypt.dll`, а это не всегда
там, где написано в настройках. Сервер открывает библиотеку
относительным путём, а Windows разбирает относительный путь по своему
порядку поиска, и каталог самой программы в нём стоит раньше рабочего
каталога: если рядом с `primitive_server.exe` лежит ещё одна папка
`mods` (а она лежит у всякого, кто собирал поставку), возьмётся она.

Мод из-за этого ищет свои скрипты не от рабочего каталога, а от
собственного файла — так что достаточно держать `dypt.dll`,
`dypt_embed.dll`, `scripts/`, `mods/` и `lib/` **в одной папке**. Какая
из копий запустится, видно в журнале: он печатает полный путь к
скриптам.

Одна тонкость, если копий всё-таки две: `mod.ron` сервер читает там,
где искал сам, а библиотеку берёт там, где её нашла Windows. Манифест и
код при этом приезжают из разных папок, и `enabled: false` в той копии,
которая не та, не выключает ничего. Проще всего копий не заводить —
либо держать их в точности одинаковыми.

## Команды

| | |
|---|---|
| `/dypt <файл> [доводы]` | выполнить скрипт из `scripts/`; расширение можно не писать |
| `/dypt eval <код>` | выполнить одну строку |
| `/dypt list` | что лежит в папке скриптов |
| `/dypt stop` | остановить то, что идёт |
| `/dypt mods` | какие скриптовые моды живут и что они ловят |
| `/dypt reload` | перечитать скриптовые моды |
| `/dypt` | напомнить это же |

Доводы приходят в скрипт списком строк: `args()`.

По умолчанию `/dypt` доступен **только операторам**, и это не
осторожность. Скрипту доступен `command()`, то есть любая серверная
команда с правами оператора; открыть `/dypt` всем — значит раздать права
оператора всем. Переключатель — `operators_only` в `mod.ron`.

## Настройки (`mod.ron`)

| ключ | что делает |
|---|---|
| `runtime` | имя библиотеки языка рядом с модом (`dypt_embed.dll`) |
| `scripts` | папка с разовыми скриптами, относительно папки мода |
| `mods` | папка со скриптовыми модами |
| `lib` | стандартная библиотека dypt; кладётся в `DYPT_LIB`, после чего работает `import "math" as math` |
| `operators_only` | кому можно `/dypt` |
| `limit_seconds` | сколько секунд разовому скрипту позволено идти; 0 — не ограничивать |
| `handler_ms` | сколько ждать ответа обработчика события; за этим сроком поток скриптов считается потерянным |
| `autorun` | что выполнить при старте сервера |

## Чего мод не умеет

**Прервать скрипт посреди счёта.** Ни в виртуальной машине языка, ни в
AST-интерпретаторе нет ни счётчика операций, ни точки, где они спросили
бы разрешения продолжать. `/dypt stop`, `limit_seconds` и `handler_ms`
работают иначе: мод начинает отвечать отказом на вызовы **в игру**, и
скрипт падает на первом же. Поэтому долгий цикл пишут так:

```dypt
while true {
    if stopped() { break }
    ...
    sleep(1000)
}
```

Цикл, который не зовёт игру и ничего не печатает, не остановит ничто,
кроме перезапуска сервера. Он займёт один поток; сервер продолжит
работать.

**Выполнять два разовых скрипта сразу.** Второй получит «уже
выполняется». Скриптовых модов это не касается — их живёт сколько
угодно.

**Ограничить скрипт в правах.** Скрипт работает правами сервера: у
языка есть `extern` к любой библиотеке системы и чтение файлов. Это и
есть причина, по которой `/dypt` по умолчанию только для операторов.

## Словарь

Ниже — всё, что скрипт может позвать. Имена нарочно не совпадают со
встроенными функциями самого dypt (`get`, `set`, `map`, `length`,
`type`...), и за этим следит тест.

Соглашения на весь список:

* **Блок** принимается числом или именем: `place(x, y, z, "stone")`.
* **Игрок** принимается числом, именем или не принимается вовсе — тогда
  это тот, кто набрал команду. Из консоли сервера «того, кто набрал»
  нет, и такой вызов отвечает отказом.
* **Координаты ячейки** округляются вниз, а не отбрасыванием дробной
  части: `pos()` даёт дробные числа, и на отрицательной половине мира
  разница — целая ячейка.
* `null` возвращается там, где ответа нет: незагруженный чанк, пустой
  слот, отсутствующее имя. Ошибка — только там, где вызов не мог
  состояться.

### Кто и что

| | |
|---|---|
| `me()` | номер того, кто запустил (0 — консоль или автозапуск) |
| `args()` | доводы командной строки, списком строк |
| `say(текст)` | всем в чат |
| `tell(игрок, текст)` | одному |
| `note(текст)` | в журнал сервера |
| `command(строка)` | серверная команда с правами оператора |
| `stopped()` | попросили ли остановиться |

`print` из самого языка уходит в чат тому, кто запустил скрипт.

## Что лежит в `scripts/`

| | |
|---|---|
| `probe.dpt` | проверка, что мост жив; работает и из консоли сервера |
| `hello.dpt` | самый маленький скрипт, который что-то знает об игре |
| `survey.dpt` | что вокруг: биом, свет, соседи, вещи |
| `tower.dpt` | башня перед игроком — то, ради чего это всё |
| `watch.dpt` | скрипт, который живёт: следит за игроками, пока не `/dypt stop` |

...и в `mods/`:

| | |
|---|---|
| `bedrock.dpt` | бедрок не ломается — весь мод в семь строк |
| `welcome.dpt` | встречает пришедших и считает их: состояние живёт между событиями |

## Как это устроено

```text
сервер игры ──C ABI──> dypt.dll (мод) ──C ABI──> dypt_embed.dll (язык)
 primitive_modapi                                 своя сборка, свой репозиторий
```

Границ две, и вторая не лишняя: dypt живёт в своём репозитории, и
зависимость по пути на него означала бы, что игра перестаёт собираться
на машине, где этого каталога нет. Договор второй границы — три функции
и три структуры; он описан в `embed/src/lib.rs` со стороны языка и
продублирован в `src/lib.rs` со стороны мода, как дублируется всякий
заголовочный файл C. Совпадение проверяется числом `DY_ABI`, и мод
спрашивает чужое первым делом.

Подробности решений — в шапке `src/lib.rs`, а со стороны языка — в
`embed/src/lib.rs` его репозитория.
